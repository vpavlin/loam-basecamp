# Loam's delivery wire, for any Basecamp core

`delivery_transport.hpp` is how loam_core talks to `delivery_module`, as a header an app core can
vendor to talk to `delivery_module` directly, with the same wire. Use it when an app must depend
only on official modules (the official catalogue) but still interoperate with Loam phones and with
apps on loam_core.

- Needs: nlohmann/json and `segment_compat.hpp` (next to it). No OpenSSL, no Qt.
- Vendor both files by commit and check `LOAM_DELIVERY_WIRE_VERSION`.
- Build `Ops` from your generated `delivery_module` client (async calls; the RAW `messageReceived`
  event payload, not the generated bytes conversion), `Config::nodeConfigJson` from
  `nodeConfig(appSettings, rln)`, then `start()`, `join(topic)`, `send(topic, bytes)`, and call
  `tick(nowMs)` every few seconds.
- One node per Basecamp: the first module to call `createNode` sets its config. The transport
  adopts a node another module created ("Context already initialized"), so loam_core and direct
  apps can run side by side. On development machines, set
  `LOGOS_DELIVERY_RLN_PRESETS={"logos.test":{"enabled":false}}` (a file path in Basecamp's
  environment) so an app that passes the RLN-on `"logos.test"` preset first doesn't break
  everyone's sends.

What stays in loam_core and is lost when going direct: the BLE and Shrooms mesh bearers, the Loam
UI's per-app view, Keycard identity signing, and the planned device-wide RLN pacer.

Tests: `core/test/delivery_transport_test.cpp` (vectors, config, lifecycle against fake Ops). The
vectors (`core/test/delivery_vectors.json`) are also run by loam-transport
(`test/delivery-vectors.test.ts`): change both together and bump the wire version.
